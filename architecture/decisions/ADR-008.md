# ADR-008: Reviewer independence through a separate job, a different model, withheld artifacts and an evidence gate

**Status:** Accepted (2026-11-21)

## Context
The reviewer must see only the issue, the diff and the repo at the PR's latest commit, may run
code, and must not see the implementer's reasoning or be able to push. LLM reviewers tend to
approve: they read a plausible diff, agree with its framing and say "LGTM". Independence of
inputs alone does not fix that; the reviewer also needs a reason to look for failures.

## Decision
Independence on five separate axes:
1. **Process:** `review_1` / `review_2` are separate jobs on fresh VMs. Nothing from the build VM
   exists there except the named artifacts it downloads.
2. **Inputs:** raw issue, a diff the harness computes itself (`git diff base...head`, not the
   Builder's `diff.patch`), and a checkout of the PR head. Not the spec, design, test report, PR
   body or any transcript (ADR-003).
3. **Model:** `gemini-3-flash-preview`, a different family from the Gemma workers (ADR-006).
4. **Permissions:** token `contents: read`; tools read/ls/grep/run in a read-only, network-less
   sandbox. The review is posted by the harness after the agent exits, so the agent never holds
   `pull-requests: write`.
5. **Incentive and evidence:** its prompt asks it to try to break the change: write a probe test
   from the issue and run it. The harness rejects an `approve` verdict if the agent executed no
   command, and drops findings that cite no file/line or command output.

Verdict JSON: `approve | changes_requested`, each finding tagged `approach` (goes back to Design)
or `code` (goes back to Implementation).

## Alternatives considered
- **Same job, new prompt.** Cheap, but the filesystem still holds the transcripts and artifacts.
  Rejected.
- **Give the reviewer the spec to review against.** Easier, but it then inherits the Analyst's
  reading and cannot notice spec drift. Rejected.
- **Majority vote of several reviewers.** More robust, but multiplies free-tier calls. Rejected for
  now.

## Consequences
- An approval always comes with at least one command the reviewer ran.
- The reviewer may raise false positives because it does not know the spec's decisions; these cost
  a rework round (at most two).
- Planned experiment E1: this reviewer vs a naive one (same model as the Builder, given spec,
  design and the Builder's summary, no evidence gate) on 5 seeded PRs with known defects. Measure
  defects caught and false approvals.
