# ADR-007: Code decides every check; tests must be red on base and green on head

**Status:** Accepted (2026-11-21)

## Context
Each stage has a check that must pass before hand-over. If an LLM judges its own output it will
usually say it passed. The testing check ("all new and existing tests pass") is especially weak on
its own: a test that does not exercise the change, or asserts the old behaviour, passes too. An
agent asked to "make tests pass" has every reason to write such tests.

## Decision
Every check is code. No LLM certifies its own stage.

| Stage | Check |
|---|---|
| 1 Requirements | `spec.md` parses; at least one `AC-n`; each AC has Given/When/Then; fuzzy-word lint on ACs (word list from the A1 skill: fast, easy, robust, ...). |
| 2 Design | A Changes table of `file::function`; each file exists and each function exists in it per Python AST, or is marked NEW. |
| 3 Implementation | Diff non-empty, inside `tinydb/` only; `compileall` and `import tinydb` succeed in the sandbox. |
| 4 Testing | Every AC id appears in a test name under `tests/autose/`. **Red/green:** each AC's test is run against the base commit and must fail, then against head and must pass. Full suite passes on head. |
| 5 Release | PR open; CI job (full pytest + mypy) green on PR head. |
| 6 Review | Verdict JSON valid; evidence gate (ADR-008). |

The red/green check is the key one. A test that passes on the base commit does not detect the
change, so it cannot verify the acceptance criterion; the gate rejects it and returns the Tester's
work with the list of vacuous tests. This is mutation testing in its simplest form, with the base
commit as the single mutant.

## Alternatives considered
- **LLM judge per stage.** Can judge prose quality, but it is a second opinion from a model of
  similar strength, it costs calls, and it can be talked round. Rejected as the deciding check.
- **"All tests pass" only.** The assignment's minimum. Accepts vacuous tests. Rejected.
- **Full mutation testing (mutmut).** Stronger, but minutes per run and noisy on a small diff.
  Rejected for time.

## Consequences
- A stage can only pass by producing something a program verified.
- Red/green assumes the behaviour is new or broken on base. For a pure refactor or a doc-only change
  the check would wrongly fail; the spec can mark an AC `regression-only`, in which case only
  "green on head" is required, and the report flags it.
- The gates check form, not meaning: a syntactically perfect but wrong AC passes stage 1. The hidden
  tests and the reviewer are the backstops.
- Planned experiment E2: run with the red/green check on and off, and count how many accepted test
  suites contain tests that already pass on base.
