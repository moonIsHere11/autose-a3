# ADR-002: Control flow is a code state machine inside an unrolled, bounded Actions DAG

**Status:** Accepted (2026-11-21)

## Context
The workflow has loops: failing tests go back to implementation, repeated failures go back to
design, and review can send work back to design or implementation, at most twice. Something has to
decide when to go back, and the loops must terminate. GitHub Actions jobs form a directed acyclic
graph (`needs:`), so a job cannot loop back to an earlier job. Events created with `GITHUB_TOKEN`
(pushes, comments, labels) do not start new workflow runs, so a run cannot re-trigger itself to
form a loop without a personal access token.

## Decision
- One workflow, `.github/workflows/autose.yml`, with the review loop **unrolled**:
  `gate -> build -> ship_0 -> review_1 -> rework_1 -> ship_1 -> review_2 -> finalize`.
  `rework_1`, `ship_1` and `review_2` run only if `review_1` requested changes (job `if:` on the
  verdict output).
- Inside `build` (and `rework_1`), a deterministic Python state machine runs stages 1-4 with
  explicit back-edges and budgets: test failure goes back to Implementation with the failure output
  (3 attempts); when those are used up, back to Design once; then stop with an explanation in the
  artifact. Spec and design gate failures get 2 retries with the gate's feedback.
- Code, never an LLM, decides every transition. An agent can produce an artifact; only a gate can
  move the run forward or back.
- Review-only mode: `/autose review` on an open PR runs `gate -> review_1` only (used for the
  seeded-PR experiment).

## Alternatives considered
- **LLM orchestrator / planner.** Can adapt the plan, but termination and the "at most twice"
  rule then depend on the model following instructions. Gemma is also our weakest link at
  structured long-horizon control. Rejected.
- **Self-chaining runs** (each stage dispatches the next run). Needs a PAT because
  `GITHUB_TOKEN` events do not trigger workflows; a PAT in the workflow is a bigger secret than we
  want. It also splits one logical run across several run pages, which hurts traceability.
  Rejected.
- **Everything in one job, loop in Python.** Simplest, but the reviewer would share the VM,
  filesystem and process with the builder, which weakens independence (ADR-008). Rejected.

## Consequences
- The two-round bound and the reviewer's fresh context come from the graph's structure: there is
  no `review_3` job and each review job starts on a new VM. Nothing an LLM writes can raise the
  bound.
- The full run is visible on one Actions run page as a graph.
- Cost: the YAML is longer and partly duplicated (`ship_0`/`ship_1`, `review_1`/`review_2`).
  Changing the round limit means editing the graph.
- Each job pays setup time (checkout, Python, Docker image), roughly 1 minute per job.
