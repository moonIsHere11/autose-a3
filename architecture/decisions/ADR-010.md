# ADR-010: Triggered by maintainers only; one queued run per issue

**Status:** Accepted (2026-11-21)

## Context
The assignment's sketch triggers on `issues: labeled` and `issue_comment: created`. Anyone can
comment on a public repo's issue, so a comment trigger without a permission check lets strangers
spend our API quota and start runs. Two triggers on the same issue (label plus comment, or two
comments) would race on the same branch and PR.

## Decision
- Events: `issues: [labeled]` with label `autose` (full run); `issue_comment: [created]` with body
  starting `/autose` on an issue (full run) or `/autose review` on a PR (review-only mode).
- The `gate` job checks the sender's repository permission (`write`, `maintain` or `admin`) through the API for both
  events. (An `author_association` check was planned, but the permission check is stricter and is what is implemented.)
  Bot senders are ignored, so the workflow's own comments cannot re-trigger it.
- `concurrency: autose-<issue number>`, `cancel-in-progress: false`: a running run is never cancelled; runs on
  different issues proceed in parallel. GitHub keeps at most **one pending** run per group: if a third event arrives
  while one run is running and one is pending, the pending one is cancelled. Because concurrency is set at the workflow
  level, any comment on the issue (even one the `gate` job will reject) joins the group, so it can displace a pending
  `/autose` run. Moving `concurrency` to the jobs after `gate` would avoid that (not done).
- Workflows run only in our fork. Workflows triggered from forks of our fork receive no secrets,
  and we do not use `pull_request_target`.

## Alternatives considered
- **Run on every new issue (`issues: opened`).** No maintainer in the loop; any user can spend the
  budget. Rejected.
- **`cancel-in-progress: true`.** Saves time on a duplicate trigger, but cancelling mid-run can leave
  a half-pushed branch and wastes tokens already spent. Rejected.
- **Global concurrency group.** Safest for rate limits, but serialises unrelated issues. Rejected;
  rate limits are handled with backoff instead (ADR-009).

## Consequences
- Only people who could push anyway can spend the budget.
- A queued duplicate run redoes the work. Acceptable: a maintainer can cancel it in the UI.
- A pending run can be displaced by an unrelated comment on the same issue (see above); the maintainer re-triggers.
- Parallel runs on different issues share one free-tier rate limit and may slow each other.
