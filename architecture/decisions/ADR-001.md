# ADR-001: Split the work into four capability profiles, not one agent and not one agent per stage

**Status:** Accepted (2026-11-21)

## Context
The six stages are fixed by the assignment. What we choose is how many LLM agents carry them and
where the boundaries between agents are. Two forces pull against each other. Fewer agents means
fewer hand-offs and less lost context. More agents means each one can be given less: fewer tools,
fewer inputs, less write access. The issue text is written by anyone who can open an issue, so it
is untrusted. And the agent that writes the code should not be the one that decides whether the
code is correct.

## Decision
Draw agent boundaries where the **capabilities** change, not where the stages change. Four LLM
roles plus deterministic code:

| Role | Stages | Tools | Write scope | Reads raw issue |
|---|---|---|---|---|
| Analyst | 1 Requirements, 2 Design | read, ls, grep | none | yes (only worker that does) |
| Builder | 3 Implementation | read, ls, grep, write, replace, run | `tinydb/` | no |
| Tester | 4 Testing | read, ls, grep, write, replace, run | `tests/autose/` | no |
| Reviewer | 6 Review | read, ls, grep, run | none | yes |

Stage 5 (Release) is not an agent. It is a script, because pushing a branch and opening a PR has
no judgement in it.

Requirements and Design share the Analyst because they need the same capabilities (read-only) and
the design depends directly on the spec. Splitting them would add a hand-off without removing any
capability.

## Alternatives considered
- **One agent for everything.** Fewest hand-offs, but that agent needs write access and the raw
  issue at the same time, so one prompt injection can edit code. It also writes the tests that
  judge its own code. Rejected.
- **One agent per stage (six agents).** Clear mapping to the table, but Requirements and Design
  would be two agents with identical permissions. That adds a hand-off and an extra prompt to
  maintain and buys no isolation. Release as an agent would put an LLM next to a write token for a
  job a script does better. Rejected.
- **Planner agent that decides which worker to call.** Flexible, but it puts control flow inside
  an LLM (see ADR-002). Rejected.

## Consequences
- Each role's capability set is small enough to state in one table row, which makes least
  privilege checkable (ADR-005).
- The Builder never reads untrusted text directly (ADR-009).
- The Tester works from the spec, not from the Builder's reasoning, so tests are less likely to
  mirror the implementation's mistakes.
- Cost: the Builder only knows the issue through the Analyst's spec. If the spec misreads the
  issue, the Builder builds the wrong thing correctly. The Reviewer reads the raw issue precisely
  to catch this spec drift (ADR-008).
- Four prompts to maintain instead of one.
